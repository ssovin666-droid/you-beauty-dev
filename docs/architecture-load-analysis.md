# Архитектура cosmi и нагрузка 1000 одновременных пользователей

Анализ ветки `codex/cosmi-star-staging` (коммит 61c91c5). Railway-окружения не проверялись: доступа к ним нет, поэтому
фактические переменные, число реплик и развёрнутые коммиты нужно сверить по разделу «Что проверить в Railway».

## Где «генерируется» существо

На устройстве пользователя. Сервер выдаёт только данные, рендер и анимация выполняются в Telegram WebView.

| Шаг | Где | Файлы |
| --- | --- | --- |
| Тип и акцент (самый частый `shade_group` на Полке) | сервер, 1 SQL-запрос + подсчёт в Python | `backend/app/services/character.py` (`compute_archetype`, `evaluate_character`) |
| Уникальная форма | сервер один раз выдаёт `shape_seed`, клиент детерминированно строит лучи | `character.py` (`new_shape_seed`), `frontend/src/lib/character/shape.ts` |
| 3D-сцена, капсула, распаковка | устройство, three.js (WebGL), отдельный ленивый чанк ~140 КБ gzip | `frontend/src/lib/character/scene.ts`, `components/character/CosmiStar.tsx`, `vite.config.ts` |
| Fallback без WebGL | устройство, статичный SVG | `frontend/src/lib/character/fallback.ts`, `env.ts` |
| Капсула на главной | статичные webp + CSS | `frontend/src/assets/character/capsule-*.webp` |
| PNG-карточка для сторис | рисуется на устройстве (canvas), загружается на сервер и хранится в PostgreSQL (bytea) | `frontend/src/lib/character/card.ts`, `backend/app/api/character_routes.py`, `models/character.py` (`ShareCard`) |
| Распознавание фото товара | сервер → OpenAI | `backend/app/services/recognition.py`, `POST /api/recognize` |

Вывод: генерация существ CPU/GPU Railway почти не нагружает. Нагрузку на сервер создают обычные API-запросы
(`/tracked`, `/character`), фоновые задачи бота и OpenAI-распознавание.

## Выдержит ли текущий API 1000 одновременных пользователей

Нет — и проблема не в существах, а в конфигурации API. Проверено нагрузочным тестом: тот же код FastAPI, локальный
PostgreSQL 16, 30 000 товаров каталога, 300 пользователей, 900 подписок. Один «пользователь» = открытие главной:
`GET /tracked?list_type=wishlist`, `GET /tracked?list_type=shelf`, `GET /character` одновременно.

| Сценарий | 20 польз. | 200 польз. | 1000 польз. |
| --- | --- | --- | --- |
| Исходный код | — | 102 × 500, 166 тайм-аутов, 120 с | 1000 тайм-аутов |
| Новый код (без ограничения) | 40 × 500 за 30 с | 105 × 500, 165 тайм-аутов | 1000 тайм-аутов |
| Новый код + семафор 12 запросов в обработке (только в тестовом стенде) | p95 0,7 с | p95 8,3 с, 0 ошибок | p95 32 с, 0 ошибок |
| Исходный код + тот же семафор | p95 1,2 с | p95 11,1 с, 0 ошибок | — |

### Узкие места (по убыванию важности)

1. **Взаимная блокировка пула соединений и пула потоков (риск падения №1).**
   `get_current_user` (`backend/app/services/telegram_auth.py`) — синхронная зависимость, которая берёт сессию через
   `get_db` (`backend/app/db/session.py`) и держит соединение до конца запроса. Синхронный обработчик ждёт свободный
   поток из пула AnyIO (40 потоков). Пул SQLAlchemy — 5 + 10 = 15 соединений. При >15 параллельных запросах потоки,
   ждущие соединение, занимают все места, а запросы с соединением не получают поток → все висят до `pool_timeout`
   (30 с) → `QueuePool limit ... TimeoutError` и 500. В логах теста — 760 таких ошибок. Хватает 20 одновременных
   открытий мини-аппа. Это не перегрузка CPU или PostgreSQL: оба почти простаивают.
   *Исправление без затрат:* ограничить число запросов в обработке ниже размера пула (async-семафор/middleware на `/api`,
   либо `--limit-concurrency` у uvicorn с ответом 503), держать `pool_size + max_overflow` ≥ этого лимита.
   Проверено в стенде: ошибки исчезают.
2. **Один процесс uvicorn** (`backend/Procfile`, `docs/testing-release.md`): все запросы на одном ядре Python.
   1000 одновременных открытий обслуживаются ~30 с (≈ 90 запросов/с). Для пика — 2 воркера/реплики после пункта 1.
3. **N+1 запросы в `/tracked`** (`backend/app/api/routes.py`: `tracked`, `serialize_tracked_item`, `get_offer_payload`):
   на каждый товар 2 дополнительных запроса (Offer+Store и валюта). 30 товаров = ~60 запросов на один экран.
4. **Тяжёлое сопоставление прямо в запросе.** `GET /tracked` вызывает `ensure_product_offer` для каждого товара без
   Offer → `link_product_to_best_match` → до 5000 строк каталога целиком (с `raw_params` и URL) и
   `SequenceMatcher` в Python. Несопоставленный товар искался заново при каждом открытии экрана.
   *Исправлено* в этой ветке отрицательным кэшем и лёгкими кандидатами (см. `docs/railway-cost-plan.md`).
5. **`GET /character` пишет в базу при каждом показе** (`evaluate_character` → `commit`) — лишняя запись на чтение.
6. **`POST /api/recognize` без авторизации и лимита размера** (`routes.py`): читает весь файл в память и тратит
   OpenAI-квоту для любого, кто знает адрес. Риск по деньгам и RAM, а не по CPU.
7. **PNG сторис в PostgreSQL** (`ShareCard`, ≤4 МБ): каждая отдача — egress из базы. При вирусности карточек это
   заметный трафик; заголовок `Cache-Control: immutable` частично спасает.
8. **Фоновые задачи бота** — главный источник трафика и записи в БД (см. ниже и `docs/railway-cost-plan.md`).

### PostgreSQL, CPU, RAM

- *PostgreSQL:* соединений хватает (API 15 + бот 15 + блокировки ≪ 100). Основная нагрузка — фоновые задачи:
  исходный импорт переписывает все строки каталога каждые 3 часа (в тесте таблица распухла с 67 до 151 МБ после двух
  импортов), а 5-минутная проверка читала тысячи полных строк каталога. Это давит на память (кэш страниц) и диск.
- *CPU API:* `SequenceMatcher` по кандидатам и сериализация; при пункте 4 до 5000 сравнений на товар в запросе.
- *RAM API:* `/recognize` и `/character/share-card` держат файлы целиком; при 1000 одновременных загрузок по 4 МБ — до
  4 ГБ. Нужен лимит размера и одновременных загрузок.
- *Frontend:* three.js грузится лениво, рендер останавливается вне экрана, DPR ≤ 2, есть SVG-fallback — на сервер это
  не влияет. Риск на слабых телефонах уже учтён в `env.ts`.

## Что проверить в Railway (без изменений)

- Какой коммит/ветка развёрнуты в API, боте и фронтенде production (Deployments → commit SHA). Локальный `main`
  = 94f35dc; фоновые задачи в `main` и в этой ветке совпадают, отличаются только тексты.
- Переменные бота: `DISCOUNT_STATE_CHECK_SECONDS`, `GOLDEN_APPLE_SYNC_SECONDS` (по коду 300 и 10800, если не заданы).
- Тип `DATABASE_URL` у бота и API: после развёртывания новой версии в логе будет строка
  `DB_CONNECTION | {'host_kind': 'railway_public_proxy' | 'railway_private' ...}` без хоста и пароля.
  Раз бот и база в разных проектах, приватная сеть между ними невозможна — подключение идёт через публичный прокси.
- Сколько реплик у API и бота, и не работает ли второй бот (тестовый проект `you-beauty-test` тоже запускает свой
  импорт каталога каждые 3 часа в свою базу).
